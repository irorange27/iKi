# 3 万字论文章节写作规划

## 目标

这份规划面向当前题目：

- `基于Agent的桌面宠物交互系统设计与实现`

正文主线保持为：

- 桌面宠物系统
- affect-aware policy
- 系统实现 + 实验验证

建议采用的字数目标不是“刚好 30000”，而是：

- 正文目标：`28000 - 32000` 字
- 含中英文摘要、致谢、参考文献前说明等整体可见篇幅：`30000+`

原因很简单：

- 本科论文后期删字比硬凑字更容易
- 第 5 章插入图表、表格和案例后，正文会自然继续膨胀

## 每章应该写什么

## 第 1 章 绪论

### 目标

- 让老师快速知道你在解决什么问题
- 说明这不是泛泛的“桌宠界面项目”
- 把论文问题收束成“情感感知如何影响 Agent 干预策略”

### 建议控制

- `4500 - 5500` 字
- 当前已经基本够用，不要把太多技术细节塞进来

### 重点写法

`1.1 研究背景与意义`

- 写大模型 agent 从聊天走向任务执行
- 写桌面端 personal agent 的价值
- 写真实场景里任务和情绪是纠缠的
- 点出“只会给答案”会带来不当干预

`1.2 国内外研究现状`

- 分三条线写：agent 与工具调用、情感计算、桌面陪伴式交互
- 每条线都要写“做到哪了”和“还缺什么”
- 结尾一定要有“研究空缺收束”

`1.3 研究问题与研究目标`

- 明确写出 3 个研究问题
- 研究目标最好和后文的第 4 章、第 5 章一一对应

`1.4 研究内容与技术路线`

- 用流程化语言写，不要只列名词
- 可以加一张技术路线图

`1.5 论文创新点`

- 最多 3 点
- 不要把普通实现写成“重大创新”
- 用“系统层、机制层、评测层”这三个层面最稳

`1.6 论文结构安排`

- 简洁即可

### 还能补什么

- 国内外研究现状再加 2-4 篇正式引用
- 技术路线图
- 研究边界简短说明

## 第 2 章 相关理论与关键技术

### 目标

- 不是堆概念，而是给第 3 章和第 4 章打地基
- 解释你后面为什么这样设计系统

### 建议控制

- `5000 - 6500` 字
- 当前还差大约 `1000 - 2000` 字

### 重点写法

`2.1 Agent 系统与大语言模型基础`

- 解释什么是 LLM-based agent
- 说明 agent 和普通聊天模型的差异
- 写出任务、状态、动作三个核心概念

`2.2 工具调用与多模型编排技术`

- 写工具调用不是简单函数触发，而是权限与边界问题
- 写为什么单一模型不适合承担所有职责
- 写主模型、工具模型、情感模型的职责拆分

`2.3 上下文组装与记忆机制`

- 写为什么上下文装配是系统能力，不是 prompt 拼接技巧
- 写 thread summary、memory、skills、affect block 的意义
- 写长期记忆和即时上下文的区别

`2.4 情感计算与用户状态建模方法`

- 写离散标签、维度表示、belief state
- 强调本文不是心理诊断
- 强调 affect 是不确定状态信号

`2.5 桌面宠物交互与 Electron 桌面应用实现技术`

- 写桌宠为什么不是纯 UI 皮肤
- 写 Electron 在控制平面上的作用
- 写 companion 外显层为何采用 fixed mapping

### 推荐新增内容

- 增补一个小节：`2.6 本章小结`
  - 已有，但还可以再明确“这些技术怎样支撑本文”
- 可以额外扩一小段“persistent agent 与普通 assistant 的差异”
- 可以补一张“关键技术关系图”

## 第 3 章 系统需求分析与总体设计

### 目标

- 这是论文从“讲概念”进入“讲你的系统”的起点
- 这一章一定要让老师看到完整系统，不要只看见一个策略实验

### 建议控制

- `5000 - 6500` 字
- 当前最少还建议补 `1800 - 2800` 字

### 重点写法

`3.1 应用场景分析`

- 不要泛写“用户可以聊天”
- 要写具体场景：
  - 中性生产力任务
  - 情绪与任务纠缠场景
  - 桌面持续伴随场景

`3.2 功能需求分析`

- 建议分成：
  - 用户交互需求
  - 任务协同需求
  - 记忆与上下文需求
  - 情感感知需求
  - companion 反馈需求

`3.3 非功能需求分析`

- 性能
- 可扩展性
- 可审计性
- 安全边界
- 可维护性

`3.4 系统总体架构设计`

- 这是本章核心
- 建议加系统总体架构图
- 图上至少画出：
  - 桌面控制平面
  - 运行时 authority
  - 能力 harness
  - 外部模型/工具/数据库

`3.5 核心业务流程设计`

- 建议按用户一轮消息流转来写
- 最好加时序图或流程图：
  - 输入
  - affect 分析
  - context assemble
  - policy 选择
  - reply/tool
  - companion 反馈

`3.6 数据组织与模块接口设计`

- 当前这一节还能明显扩
- 可以细分：
  - 会话数据
  - affect 数据
  - memory 数据
  - benchmark 数据
  - runtime metadata

### 这一章最适合补字数的地方

- 架构图说明
- 业务流程逐步展开
- 数据表/模块接口说明
- companion 与主聊天窗口的关系

## 第 4 章 情感感知驱动的智能体决策机制设计与系统实现

### 目标

- 这是整篇论文最核心的一章
- 要真正写出“你的方法是什么”，而不是只说“系统会感知情绪”

### 建议控制

- `5500 - 7000` 字
- 当前还建议补 `2500 - 3800` 字

### 重点写法

`4.1 系统运行链路设计`

- 按“感知 -> 状态建模 -> 决策 -> 执行 -> 外显反馈”展开
- 每一步写输入、输出、作用

`4.2 情感状态表示与更新机制`

- 建议写得更技术化
- 可以补：
  - emotion event 存储
  - affect state 聚合
  - 时间衰减
  - confidence threshold
  - realtime 与 persisted 的关系

`4.3 显式干预策略模型设计`

- 这是本章最关键部分
- 要写清楚：
  - 输入是什么
  - 动作空间是什么
  - 为什么选这些模式
  - 各模式适用于什么场景

`4.4 记忆检索与上下文注入实现`

- 写 context assembler 的结构
- 写 affect block 为什么不能只是 prompt 修饰
- 写 memory block 如何受边界约束

`4.5 工具路由与任务执行控制实现`

- 这是体现“affect 真影响决策”的关键
- 写 affect 如何影响：
  - 工具审批
  - 自动工具
  - 技能路由
  - 行为保守程度

`4.6 桌面宠物反馈表现机制实现`

- 要把桌宠和内部策略真正绑定起来
- 不能只写 UI 外观
- 要写 phase mapping、why fixed mapping、why not second agent

### 推荐新增内容

- 加一个小节：`4.7 关键模块实现小结`
  - 已有，但可以更明确总结“机制如何闭环”
- 可补 1-2 张图：
  - affect signal flow
  - intervention policy state flow
- 可加伪代码：
  - affect 聚合流程
  - policy 选择流程

## 第 5 章 实验设计与结果分析

### 目标

- 这是最容易拉开论文质量差距的一章
- 也是最容易从“像课程设计”变成“像研究论文”的一章

### 建议控制

- `6000 - 8000` 字
- 当前还建议补 `2500 - 4500` 字
- 最终大概率会成为全文最长一章

### 重点写法

`5.1 实验目标与研究问题`

- 和第 1 章呼应
- 不要重复太多，强调实验要回答什么

`5.2 实验环境与对比条件`

- 一定补全：
  - 模型
  - 运行环境
  - 数据版本
  - 三种条件定义

`5.3 论文数据集构造与质量控制`

- 这一节非常适合写厚
- 可以写：
  - 为什么不用真实日志
  - 为什么用合成 decision-point benchmark
  - main set 和 neutral set 的组成
  - manifest / rewrite / audit 流程

`5.4 评价指标设计`

- 自动指标
- 人工评估
- 研究问题与指标映射

`5.5 系统功能与性能验证`

- 这是“系统层评估”
- 写功能闭环和 latency/resource

`5.6 显式情感策略对比实验与消融分析`

- 这是实验核心
- 正式跑表后要写：
  - 总体结果表
  - 分类型结果
  - 失败案例
  - 消融解释

`5.7 中性任务非劣性分析与案例讨论`

- 防止导师问：
  - “是不是只是更保守了，所以看起来更安全？”
- 这节就是回答这个问题

### 这一章最适合补字数的地方

- 数据集构造流程
- 实验环境与表格
- 结果表
- 案例分析
- 失败案例讨论

### 这一章一定要有的图表

- 数据集组成表
- 三种实验条件对比表
- 主测试集结果表
- 中性任务结果表
- 1 到 2 个典型案例对照表

## 第 6 章 总结与展望

### 目标

- 收束全文，不是机械复述目录
- 让老师看到你知道自己做成了什么、没做成什么

### 建议控制

- `1800 - 2500` 字
- 当前还建议补 `500 - 1000` 字

### 重点写法

`6.1 研究工作总结`

- 按“系统层、机制层、评测层”收束最清楚

`6.2 主要不足分析`

- 这里要诚实
- 可以写：
  - benchmark 外部效度有限
  - affect 仍以文本为主
  - companion 表现层还比较轻量
  - 结果规模和人工评估样本仍有限

`6.3 后续研究展望`

- 多模态 affect
- 更强的长期边界控制
- 更丰富的 companion 表现
- 更真实的用户研究

## 最优写作顺序

不要按 1 到 6 顺序死写，建议按下面顺序推进：

1. 第 3 章
2. 第 4 章
3. 第 5 章
4. 第 1 章
5. 第 2 章
6. 第 6 章

原因：

- 第 3、4、5 章最贴近你手上的真实项目资产
- 先把主体写厚，前后章更容易收束
- 第 1 章和第 6 章应该最后定调

## 对你当前稿子的直接建议

如果按现在仓库里的初稿状态继续推进，我建议优先补：

### 第一优先级

- 第 3 章：补系统总体架构图、业务流程图、模块与数据组织
- 第 4 章：补 affect 聚合、policy 选择、tool guardrail、companion 映射
- 第 5 章：补实验环境、数据集构造、结果表位和案例分析结构

### 第二优先级

- 第 2 章：补参考文献和理论承接
- 第 6 章：补不足与展望

### 第三优先级

- 第 1 章：做最后收束和语言精炼

## 一句话版本

- 第 3 章写成“完整系统设计章”
- 第 4 章写成“真正的方法与实现章”
